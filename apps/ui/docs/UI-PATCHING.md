# Tested UI patches

This is an optional validated frontend patch interface. The full-control agent
can also edit arbitrary host, server, dependency and UI paths directly through
its shell. These allowlists apply to this interface only. See FULL-CONTROL.md.

## Product rule and ownership

The Pi trial host owns UI patches. The agent submits complete frontend file contents through dedicated tools. Its ordinary shell tools retain the owner-authorised VM permissions. The host stages each patch outside the application, validates a disposable snapshot, then promotes it only if the live source still matches the staged base. Next.js development mode observes promoted files and reloads the browser.

Allowed paths are `app/page.tsx`, `app/error.tsx`, `app/globals.css`, component TypeScript/CSS files, and `lib/ui/` TypeScript/CSS files. Authentication, server routes, transports, environment files, dependencies and configuration are outside this interface. The host is trusted code, and accepted frontend JavaScript remains trusted code. This interface is not a hostile-code security boundary.

## Interface

`ui_source_read({path})` reads an existing allowlisted frontend file. Start with `components/live-workspace.tsx` or `components/live-workspace.css`.

`UiPatchStore` provides `stage({files})`, `validate({id})`, `promote({id})`, `rollback({id})` and `status({id})`. Files contain `path` and `content` strings. A patch contains at most 20 files, 200 KB per file and 1 MB overall. IDs are generated by the host. Stage records and validation/promotion receipts are immutable files in the trial's private patch directory.

Validation runs `npm run typecheck`, `npm run lint` and `npm run build` against a disposable source copy with its own build output. The subprocess has an empty credential environment and a networkless Bubblewrap filesystem namespace. Only the snapshot is writable; installed dependencies and the Node toolchain are read-only. Live source and agent credentials are absent from that namespace. Failed validation never changes live source.

One host instance serialises validation, promotion and rollback. A whole-source fingerprint catches stale patches and changes made during validation. Promotion writes a durable intent receipt before changing source. Startup recovery restores an interrupted promotion using staged originals when each touched file still matches its original or staged value. Unexpected external edits stop recovery rather than overwrite them. Rollback is allowed only while the complete live source still matches the promoted revision. Receipts survive a host restart.

Promotion changes several files sequentially, so a development browser can briefly observe intermediate compilation errors. Do not use this development mechanism to deploy externally. Production promotion needs a separate release boundary.

## Acceptance scenarios

- Reject traversal, symlinks, authentication/configuration/dependency paths and oversize files.
- A failed type, lint or build check leaves live source unchanged.
- A source change after staging makes validation or promotion stale.
- A valid patch passes all configured commands and changes the actual frontend source.
- Rollback restores exact previous contents, including removal of newly created files.
- An interrupted promotion recovers from durable intent without overwriting unrelated edits.
- A recreated store can read immutable receipts and roll back a completed promotion.

`node check-ui-patches.mjs` in the private Pi trial app exercises these scenarios against an isolated fixture and executes actual validation subprocesses. A separate running-browser check verifies Next.js hot reload against the real client.
